Tracetoon · graph vs relational evidence · November 2026

The graph brief wins on quality, narrowly, and the engine loses to SQLite

We built two evidence stores for Tracetoon's PR writer and gave them the same writer, reviewers, base drafts, judges and harness. The graph brief on Relate beats a relational store on quality at a similar budget. The margin is clear on Claude and thin on Codex. Separately, a straight SQLite port of the same graph queries produced byte-identical briefs about three times faster.

Verdict. On Claude, the graph brief wins on quality at the same cost. It wins 12 paired outcomes and loses 1, the composite gap is clear of zero, and it makes fewer factual errors.

On Codex, the graph brief wins narrowly on composite score, with the interval clear of zero on one of two runs. The two arms are level on errors. Relational still wins one more paired consensus outcome than the graph in both runs, and the graph costs 17–22% more per draft. That is a tie on outcomes and a small loss on cost.

A graph-specialized database should never lose to a relational database on a graph-shaped workload.

Today it does. The rest of this page shows how close the quality race was, what the relational arm did better, how a SQLite port of the same queries compares on speed, and what we would ask the Relate team to fix first.

The two arms

Both arms read the same agent session logs, the same diff and the same redacted evidence. They differ in how the evidence is stored and how the brief the writer reads is built.

Graph brief on Relate (r23)

  • Evidence graph of prompts, plans, edits, hunks, commits, runs and claims, built deterministically in Relate (WASM).
  • The brief is rendered from named Cypher queries: sentence-to-code links, new vs changed, do-not-say and limits rows, owners rows, run history, provenance from prompts and plans to surviving edits.
  • Search links: Relate's own FULLTEXT index (BM25) ties commit text, prompts and plans to hunks, stored as TIED_TO edges.
  • Tracetoon closeout commit bd55f75. Default reviewers: two cheap high-effort review passes.

Relational store (r17)

  • SQLite tables for the same evidence, with FTS5 BM25 full-text search and local embeddings (potion-code-16M).
  • The brief is a packed context of about 2,112 tokens, built by text retrieval over those tables.
  • Same reviewers and defaults, same base drafts, judges and harness.
  • Tracetoon branch r17-relational, commit 9f05d15.

The road: five rounds to pass relational

Where relational won, and where the graph did

Relational beat the r15 graph on Codex outright. It won 13 pairs and lost 1 against its own base with 0.00 factual errors. The r15 graph had 0.09 errors per judgment and lost 7 of 25 paired outcomes to relational, winning 1.

It took five rounds of brief engineering to pass it. On Codex, r21 was the first round whose interval did not dip below zero (lower bound 0.0), and r22 was the first clearly above it. The graph still trails on paired outcomes in the final two Codex runs, 4 to 5. In the first of those, relational won 4 of 5 pairs on pr11.

Several of the graph's winning features came from the relational arm. Text search that ties docs and script sentences to hunks, and code lines printed next to claims, were relational ideas we moved into the graph.

The margins are small. 25 pairs per provider is a small sample, and the case bootstrap has only 5 cases to resample.

Vector search added nothing. On Codex, BM25 plus vectors scored 3/8/14 and −0.8 against relational, worse than BM25 alone (1/7/17, +0.1).

The graph brief got bigger. Graph briefs grew 6–15% over the rounds. On Codex the larger brief is re-read on every turn, which is where the 17–22% cost gap comes from. Codex graph runs used 2.16–2.20M writer input tokens vs 1.76M for relational.

The relational arm has its own weaknesses. On pr12 it mislabeled a symbol, which walked the writer into trap T4 in 8 of 20 judgments. Its packed context has no do-not-say, process or background rows, so it has nothing to stop the writer from repeating a claim the session abandoned. Its uncertainties score on Claude was 0.52, against 0.60 for the graph.

Where graph structure won

  • Sentence-to-code links that survive later edits.
  • New vs changed, from edit lineage.
  • Do-not-say and limits rows for claims the session dropped or never checked.
  • Provenance from prompts and plans to the edits that survived. This is where context scores came from.
  • Owners rows that say where each behavior lives.
  • Run history tied to the final code.

Where relational text retrieval won early

  • Tying sentences in docs and scripts to the hunks they describe.
  • Showing the code lines and comments next to the claim.
  • Entry points at the owning file.

The shipping design is graph structure plus full-text search inside the graph database, using Relate's own BM25 index. That combination is what passed the relational arm.

The same graph queries on SQLite

Another agent ported Tracetoon's graph queries to SQLite (tracetoon branches feat/evidence-sqlite at 1e11af2 and feat/evidence-sqlite-extras). We wrote a parity port on top (branch r16-sqlite-parity, c088a54) that returns rows in the graph engine's order where the brief depends on it.

The output matches. Briefs were byte-identical on 5 dev cases × 2 layouts, with each engine reading graphs built by either engine. The SQL parity check reported "same" on 10 graphs, and the engine benchmark checked 5,784 answers with no disagreements. So the quality results above apply equally to a SQLite backend. The performance does not.

The graph engine is faster in one family of queries. A single shortest path from one Prompt to one Commit took 12–52 ms on cypherlite and 190–1,061 ms on SQLite. Single-pair path and BFS queries took 0.2–0.4 ms on cypherlite and 2–36 ms on SQLite, and the SQLite recursive CTE that returns the full path ran out of memory. Everything else, including every query Tracetoon runs to build a brief, was faster on SQLite.

Relate vs cypherlite: the gap has not closed

The engine benchmark above ran on cypherlite v0.16.1, the predecessor of Relate. When we migrated Tracetoon to Relate (bd55f75), we measured Relate aa0f79e against cypherlite on Tracetoon's own brief. query brief was 6–24% slower on Relate. Prepare time and peak memory were about equal. The Relate WASM module is 6.85 MB, against 6.50 MB for cypherlite.

Feedback for the Relate team

In priority order. File pointers are into the Relate repository at aa0f79e. The benchmark failures were measured on cypherlite v0.16.1; we have not rerun the full suite on Relate, and the code paths below are where we expect the cost to be.

  1. Make bounded var-length distinct, count and exists use the frontier kernel P1

    The worst failures are variable-length patterns whose answer is a set of distinct endpoint pairs. walk_var_length clones the row, the used-relationship set and the trail on every hop and enumerates every trail, and UsedRels is a Vec with a linear contains. A frontier kernel exists and was already in cypherlite v0.15+, yet these shapes still exploded: k-hop reach k=4 took 3,180 ms and 1,070 MB on 349 nodes and k=5 trapped at 4,072 MB, where SQLite took 72 and 149 ms. Co-change at d=4 took 7,411 ms against 37 ms. Either the gate in frontier_engages does not engage for these shapes or they do not qualify. Widen it to undirected, unlabeled-target and <>-filtered patterns, or add a planner hint.

    MATCH (p:Prompt)-[*1..k]-(n) WHERE n <> p WITH DISTINCT p, n RETURN count(*)
MATCH (a:File)-[:TOUCHES*1..2d]-(b:File) WHERE a <> b WITH DISTINCT a, b RETURN count(*)

    relate/relate-executor/src/pattern_walk/admit.rs:505 (walk_var_length) · relate/relate-executor/src/pattern_walk/mod.rs:332 (UsedRels) · relate/relate-executor/src/exec/kernels/frontier_match.rs:745 (frontier_engages)

  2. Batch shortestPath per source and recognize all-pairs patterns P1

    One shortest path per (Prompt, node) pair on 5,258 nodes took 9,129 ms at k=1 and 169,172 ms at k=3, against 7.1 and 1,678 ms on SQLite. shortest_value runs a search per row. When many rows share a source, one BFS from that source answers all of them.

    relate/relate-executor/src/eval_walk/shortest.rs:25 (shortest_value)

  3. A bulk-load API P1

    Load time grows much faster than SQLite's: 3× at 349 nodes and 16× at 26,726 nodes (23,414 vs 1,474 ms). Tracetoon loads its graph as JSON batches with per-relationship property joins. A columnar or typed-array load path with internal-id relationships would remove most of that.

  4. Cut per-call overhead: compact results, multi-query calls, plan reuse P2

    Every execute call builds a full JSON wire envelope, and Tracetoon then runs JSON.stringify on parameters and JSON.parse on the result. executeScript runs several statements but still returns one JSON envelope per statement. A compact or streaming row format and a multi-query call with shared parameters would help the brief, which runs dozens of small queries. The plan cache also drops an entry after any commit, so a load-then-query workload replans.

    surfaces/relate-wasm/src/lib.rs:78 (execute), :86 (execute_script) · relate/relate/src/plan_cache.rs · tracetoon src/graph/engine.ts:138, :147

  5. Startup and memory baseline P2

    initSync compiles the 6.85 MB module in every process, and the graph engine starts at about 18 MB of WASM memory against 8 MB for SQLite. On graphs up to 40 nodes, load took 147 ms vs 47 ms. Offer a cached compiled module, let builds drop optional features, and ship a size-optimized build (wasm-opt -Oz).

    Makefile:42 (build-wasm) · tracetoon src/graph/engine.ts:54

  6. A configurable memory ceiling with clean errors P2

    The failures above ended as WASM traps at 3.5–4.1 GB, which take the process down. A ceiling the host can set, with an ordinary query error when it is hit, would let a tool fall back to a cheaper query.

  7. Full-text analyzers at index time P3

    Relate's FULLTEXT index is true BM25 (k1 1.2, b 0.75), and the english analyzer Porter-stems the query. The index's fulltext.analyzer config is not applied to stored tokens, so a stemmed query does not meet unstemmed index terms. Tracetoon Porter-stems both the hunk text and the query in TypeScript to work around it. Apply the analyzer at index time. A code-aware tokenizer that splits camelCase, snake_case and paths would also help this workload. Quoted phrases do not yet enforce adjacency.

    relate/relate-executor/src/exec/fulltext.rs (module doc, lines 20–27) · tracetoon src/graph/porter.ts

  8. Publish prebuilt WASM artifacts P3

    There is no prebuilt relate.wasm in the repository. Building one needs binaryen in addition to the Rust toolchain, which is a hurdle for a tool that only wants to embed it.

Keep and advertise the single-pair path advantage. One-to-one shortest path and BFS were 10–100× faster than SQLite and never failed, where SQLite's recursive CTE ran out of memory returning the path. That is a real strength of a graph engine, and it should stay fast as the items above land.

Benchmark to adopt

Use the queries above as a regression suite, with the target "match or beat SQLite" on every row. The harness is scripts/bench-engines.ts on tracetoon branch feat/evidence-sqlite-extras (d7e7eb9). It runs both engines in WebAssembly on real Tracetoon graphs (7 to 876 nodes) and synthetic graphs (349 to 107,426 nodes), checks that answers agree, and records time and memory.

  • W1: the full PR workload (brief, derive, every named query).
  • B1: k-hop reach [*1..k] + DISTINCT, k = 1 to 6. B1sp: the same with shortestPath.
  • B2: co-change [:TOUCHES*1..2d], d = 1 to 4, with and without shortestPath.
  • B3: shortest Prompt→Commit path. B4: provenance chain. B5: cycle closure.
  • Path forms: single-pair path, BFS and length, prompt→hunk, commit→prompt, file→file.

Method and caveats

  • Harness. prbench-score at e7085bd plus the paired-delta script. Dataset real-cases@1.0.0, dev split: 5 real Tracetoon PRs × 5 replicates per arm.
  • Judges. Opus and Sonnet for Claude runs, Sol and Terra for Codex runs. A paired outcome counts only when every judgment agrees.
  • Δ-of-Δ. (graph − its base) − (relational − its base), with a case bootstrap of 5000 resamples, seed 7.
  • Base drafts. Shared between arms, except that Claude r20–r23 used base drafts regenerated after Claude Code updated (CLI pinned at 2.1.319). Δ-of-Δ compares each arm with its own base, which is why the rounds remain comparable.
  • Sample size. 25 pairs per provider, 5 cases. The held-out test split has not been run.
  • Engine numbers. The SQLite vs graph engine benchmark was measured on cypherlite v0.16.1 by another agent. The Relate vs cypherlite brief timings are from our own run on this machine.
  • Branches. The relational and SQLite branches live only on the steveonjava fork of Tracetoon.
